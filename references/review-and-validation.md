# 诊断与验证指南

用于较全面的审查、真实失败复盘或涉及实现的修改。选择与本次目标有关的部分，不把下表变成用户问卷。

## 从需求到实现

| 检查对象 | 要查的行为 | 典型错误 |
|---|---|---|
| 触发与任务角色 | 输入对象是谁、什么请求应启用 | 把样本客户当供方；用户只要分析却制作整片 |
| 最少输入 | 是否先查已有资料，何时必须补问 | 可查信息推回用户；歧义目标随便选一个 |
| 硬条件和偏好 | 谁确定条件、缺证据能否通过 | 把默认时长当用户要求；未知条件算已满足 |
| 示例与通用能力 | 案例是否被错误推广 | 其他产品被强加纸箱、地图、运输镜头 |
| 证据和状态 | 事实、推断、未验证、实际结果是否分开 | 候选匹配等于购买意向；导出成功等于画面合格 |
| 过程与授权 | 步骤是否服务目标、能否自主完成已授权部分 | 每步重复审批；研究任务自动发信 |
| 继续与局部改动 | 能否确定基线、保护已认可部分 | 只换音乐却重排镜头；每批重复客户 |
| 交付与验收 | 输出能否打开/使用、报告是否绑定最终版本 | 只给方案冒充成品；旧报告套到新版 |
| 模板和脚本 | 参数、分支、限制是否与文字声明一致 | 文档支持全曲，解码缓冲只够短片；静音通过同步验证 |
| 依赖与可移植性 | 核心能力是否依赖作者私有路径或未配工具 | 本机存在就宣称别人开箱能运行 |

可选的简短问题记录：位置、观察到的依据、受影响的请求、改动、验证结果。分类用“已复现缺陷/规则冲突/尚未实测的潜在风险”，无需伪精确总分。

## 如何选测试

先把要求变成可观察结果，再选最少充分的案例。以用户请求和原始素材为输入，检查产物及实际状态；不要只搜索提示词中是否出现“必须验证”。

- **正常路径：** 完整输入应成功；修复后不能只验证坏输入会失败。
- **关键缺失：** 真缺失应补问或标未核；可自行查到的不能推给用户。
- **范围覆盖：** 用户自定义数量、画幅、格式或“只改一个部分”必须优先于默认值。
- **失败与恢复：** 验证器是否拒绝缺流、静音、空文件、过期证据等本任务相关缺陷；旧成功报告能否错误掩盖这次失败。
- **继续/切换：** 该保留的状态继续沿用；换公司、歌曲或产品时该隔离的资料不能混用。

脚本缺陷尽可能先建立能区分旧问题和正常结果的复现样本。修复后运行同类输入；不通过时看实际日志，不改预期来迎合错误实现。可复用且有价值的回归测试可随技能保留，测试产物放临时目录；一次性检查不必变成永久测试体系。

结构验证器只证明它实际检查的字段，不验证业务能力。人工沿读情境叫“人工情境复核”，不能称“独立代理实测”。只有真正产出并检查完整成果，才报告对应业务实测；媒体的完整解码、抽帧、观看和试听分别记录。

## 跨行业迁移检查

当技能声称跨行业/跨题材时，至少考虑一个与原案例明显不同的合理场景。目的在于发现隐藏的固定品牌、地区、重量、镜头、时长等，不是强迫原本专用的技能变通用。专用技能可以保留恰当风格和参数，只需说明适用范围与用户覆盖方式。

## 停止条件与报告

当前目标的明确缺陷已修复、相关检查通过、未验证项已说明后交付，不追求没有边界的“完美”。依赖或权限阻塞时保留可复现信息，说明具体缺项；不要通过换一个较弱的检查器把失败变成通过。

报告可以只有几行：问题/改动、真实运行的检查、结果、未覆盖范围。保存报告时放用户工作目录；公开测试只保留合成或适合公开的素材，不公开内部业务记录。
