# 本地同步与公共发布

仅在任务涉及安装、多个副本或仓库更新时阅读。优化方法不绑定 GitHub CLI、特定用户名或固定盘符；使用当前可用的正常认证工具，不读取或输出密钥。

## 确定同步范围

- 用户指定本地技能：更新目标安装版，可保留工作源码；不自动创建公共仓库。
- 用户明确要求优化其仓库：按已授权仓库范围修改和提交，沿用仓库分支/PR规则；不要扩大到账号下无关项目或改变可见性。
- 只要求检查或给建议：不写入、不发布。
- 多个副本：比较原版与当前内容，区分真实修改和换行差异。存在用户本机偏好时合并保留，不能整目录覆盖。
- 平台管理的插件缓存：优先定位可维护源和受支持更新路径，不把修改缓存冒充长期安装完成。

新技能默认按环境的技能目录规则安装。已安装技能的个人偏好、历史工程定位可保留在本机；公开版只保留通用流程。未安装的其他技能不因一次仓库优化就自动安装。

## 发布前形成具体载荷

需要公共发布时，先完成修改与验证，再审查明确文件清单和完整差异。检查新文件的全文；不能只看统计或只扫几个关键词。重点查：个人邮箱/账号、内部客户资料、真实案例反馈、凭据、本机路径、项目历史和无关素材。

同时检查输出仍完整：不要误删必要引用、素材、许可说明或运行脚本来“脱敏”。真实公共依赖和用户明确要公开的信息按实际授权处理，不把所有网址或公司名一律删除。

采用以下最小可靠流程：

1. 记录远程基线和本地改动，逐文件确定要发布的通用版本；不从包含本机档案/备份的目录整批上传。
2. 核对已审内容对应的文件路径和哈希；内容在审查后变化则重新检查。范围很小的修改不强制额外造复杂工具链。
3. 更新前检查远程是否前进；有变化先合并/重审，不强推覆盖。不改变用户未要求的仓库公开性、权限或分支保护。
4. 通过正常认证提交。若常规 Git 传输失败，可在相同授权与审计范围内用可用官方 API；不能用另一工具绕过审批拒绝。
5. 核实远程提交和文件内容，再宣称已发布。未知结果先只读核实，不盲目再次提交。需要 PR 时按环境要求关联它。

自动审批拒绝后，说明被拒动作与理由。可先补齐证据或缩小为更安全的具体操作再送审；无法消除阻塞时向用户解释并求助，不规避拒绝。此前用户的有效授权仍应考虑，不把工具故障都变成重复的权限询问。

## 验证副本与清理

同步后核对文件内容、引用和本机上下文是否保留。工作源码、安装版和公共版有意不同应说明原因，不为追求哈希一致而泄漏私人信息。

保留必要的回滚基线、最终修改和简短验证记录。删除本轮可重建缓存、下载工具和重复载荷前，先解析并检查确切绝对路径及所属工作目录；不删除唯一证据、凭据配置、用户原始资料或已编辑产物。不要为清缓存重新下载同一大工具。
